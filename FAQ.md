# FAQ: состояние диалога и генерация ответа

Этот документ описывает два варианта чата: обновление состояния отдельным шагом
с последующей генерацией ответа и прямой ответ по переписке. Он фиксирует
предлагаемый протокол, состав входных секций и обучающих целей. Наличие описания
не означает, что все эти режимы уже реализованы.

Примеры сообщений приведены на английском, как в текущем датасете. Пользователь
всегда начинает диалог. В качестве базовой модели используется предобученная `gpt2`.

## 1. Какие варианты мы сравниваем и что уже работает?

| Вариант | Вход | Генерируемый результат | Статус |
| --- | --- | --- | --- |
| Текущий UBAR | Переписка с предыдущими состояниями и действиями | Состояние → действие → ответ | Обучение, бенчмарк и чат реализованы |
| Обновление состояния отдельной задачей `dst` | Предыдущее состояние и переписка | Полное состояние | Реализовано; для предлагаемой цепочки требуется согласовать момент предыдущего состояния |
| Предлагаемая цепочка из двух шагов | Предыдущее состояние и переписка → обновлённое состояние и переписка | Состояние → ответ | Требуется реализация ответа без входного действия и соединение шагов |
| Прямой ответ `history` | Только инструкция и переписка | Ответ | Обучение и отдельная оценка реализованы; поддержка в чате ещё нужна |

Ниже задача ответа по состоянию условно называется `state_response`. Это
**предлагаемое имя**, которого сейчас нет среди допустимых значений `--task`.

Текущий `response` имеет другой контракт: он обязательно получает и состояние,
и готовое действие. Просто убрать `action` из его запроса недостаточно.

## 2. Что здесь называется секцией?

Секция — логическая часть входа модели. Она не требует отдельного специального
токена или ChatML. В формате `plain` инструкция и состояние могут находиться
в сообщении `system`, а переписка — в сообщениях `user` и `assistant`.

| Секция | Что содержит | Кто её предоставляет |
| --- | --- | --- |
| Инструкция задачи | Что нужно предсказать, какие данные учитывать, какой формат вернуть | Приложение; при обучении используется тот же контракт |
| Предыдущее состояние | Последний сохранённый снимок памяти | Приложение читает прошлое предсказание; на первом ходе создаёт пустое состояние |
| История | Предыдущие сообщения пользователя и фактически выданные ответы ассистента в хронологическом порядке | Приложение |
| Новое сообщение | Текущий ввод пользователя | Пользователь |
| Текущее состояние | Результат извлечения на текущем ходе | Модель на первом шаге |
| Цель обучения | Ожидаемый JSON либо реплика | Датасет; это `completion`, а не часть входного запроса при использовании модели |

Последнее сообщение пользователя включается **один раз**. Можно хранить его
отдельно при сборке запроса, но в готовом массиве `messages` оно становится
последним сообщением `user`. Если оно уже есть в истории, повторять его не нужно.

Поля `episode_id`, `turn`, `view`, `next_turn` нужны для связывания примеров,
отчётов и диагностики. Передавать их модели как содержание диалога не требуется.

## 3. Что передавать на шаг обновления состояния?

Для двухшагового режима фиксируем момент сохранения памяти:

- `U_t` — сообщение пользователя на ходе `t`.
- `S_t` — состояние после обработки `U_t`, но **до** ответа ассистента `R_t`.
- `H_t` — вся передаваемая переписка до `U_t`, включая предыдущий ответ `R_(t-1)`.

Первый шаг имеет контракт:

```text
Инструкция обновления + S_(t-1) + H_t + U_t → S_t
```

На первом ходе `S_(t-1)` — пустой снимок, а `H_t` — пустая история. На следующих
ходах предыдущее состояние ещё не учитывает последний ответ ассистента.
Модель должна учесть этот ответ, затем новое сообщение пользователя и вернуть
обновлённый снимок.

| Секция | Что должно быть | Чего не должно быть |
| --- | --- | --- |
| Инструкция | Требование вернуть полный JSON состояния; сохранять накопленные факты и отказы; учитывать последний ответ ассистента и новый ввод | Требование заранее выбрать следующее действие или написать ответ |
| Предыдущее состояние | Последнее сохранённое `S_(t-1)` с определённой выше границей времени | Состояние из будущего хода или скрытые факты симулятора |
| История | Реальная предыдущая переписка, включая `R_(t-1)` | Будущий ответ и эталонный ответ, подставленный вместо фактически сгенерированного |
| Новое сообщение | Точное текущее сообщение пользователя | Его дублирование в другой части запроса |

Возможный шаблон для `plain`:

```text
system: Update the dialogue state using the conversation and the latest user message.
The previous state was saved before the most recent assistant reply.
Account for that reply and then the latest user message exactly once.
Use earlier history as context; do not count earlier questions again.
Preserve known facts and refusals. Do not invent unobserved information.
Return only the complete state as a JSON object.
Previous state: {previous_state_json}
{history_messages}
user: {user_message}
assistant:
```

Это предлагаемый шаблон, а не дословная копия текущего `task_messages('dst', ...)`.
Значения в фигурных скобках подставляет приложение. `history_messages` — сообщения
с ролями; на первом ходе эта подстановка пустая.

Повторный запрос на генерацию не должен повторно увеличивать счётчики: модель
получает тот же исходный снимок и ту же переписку. Не следует сохранять частично
обработанный ход как новое исходное состояние.

## 4. Как выглядит пустое состояние и что означает каждое поле?

Пустой снимок соответствует `State().snapshot()` из
[dialogue_protocol.py](dialogue_protocol.py):

```json
{
  "known": {
    "time_of_day": null,
    "activity": null,
    "mood": null
  },
  "statuses": {
    "time_of_day": "unknown",
    "activity": "unknown",
    "mood": "unknown"
  },
  "asked": [],
  "pending": null,
  "attempts": {
    "time_of_day": 0,
    "activity": 0,
    "mood": 0
  },
  "topic": "daily_routine",
  "followup_used": [],
  "user_question_pending": false,
  "wants_exit": false,
  "phase": "opening",
  "last_action": null
}
```

| Поле | Содержание и назначение |
| --- | --- |
| `known` | Известные значения слотов. `null` означает отсутствие известного значения, а не конкретный ответ пользователя |
| `statuses` | Состояние каждого слота: неизвестен, ожидает ответа, известен, отклонён пользователем, неоднозначен или пропущен |
| `asked` | Журнал слотов, о которых уже спрашивал ассистент. Это список; повторные попытки могут давать повторные записи |
| `pending` | Слот, по которому ожидается ответ. В текущих эталонных данных после обработки нового пользовательского сообщения это поле сбрасывается в `null` |
| `attempts` | Число уже сделанных запросов или уточнений по каждому слоту. Сообщённый пользователем без вопроса факт не увеличивает счётчик |
| `topic` | Текущая тема разговора |
| `followup_used` | Темы, для которых ассистент уже использовал продолжение разговора; в JSON хранится список |
| `user_question_pending` | Требуется ли ответить на вопрос из текущего сообщения пользователя |
| `wants_exit` | Выразил ли пользователь желание закончить разговор |
| `phase` | Стадия диалога: `opening`, `exploration` или `closed`; смысл переходов должен соответствовать обучающей разметке |
| `last_action` | Тип предыдущего действия ассистента. Это память о прошлом, а не план следующего ответа |

Допустимые значения слотов на момент описания:

| Слот | Значения |
| --- | --- |
| `time_of_day` | `morning`, `afternoon`, `evening`, `night` |
| `activity` | `reading`, `working`, `listening_to_music`, `relaxing` |
| `mood` | `calm`, `happy`, `tired` |

Значения `statuses`: `unknown`, `pending`, `known`, `declined`, `ambiguous`,
`skipped`. Допустимые темы: `daily_routine`, `books`, `work`, `music`, `relaxing`,
`python`. Точные ограничения проверяет `validate_state()`.

`declined` позволяет отличить отказ от отсутствия информации: неизвестный факт
сам по себе не означает, что о нём следует спрашивать снова.

## 5. Что именно возвращает первый шаг?

Для первого сообщения:

```text
It is evening.
```

ожидаемый полный снимок состояния выглядит так:

```json
{
  "known": {
    "time_of_day": "evening",
    "activity": null,
    "mood": null
  },
  "statuses": {
    "time_of_day": "known",
    "activity": "unknown",
    "mood": "unknown"
  },
  "asked": [],
  "pending": null,
  "attempts": {
    "time_of_day": 0,
    "activity": 0,
    "mood": 0
  },
  "topic": "daily_routine",
  "followup_used": [],
  "user_question_pending": false,
  "wants_exit": false,
  "phase": "opening",
  "last_action": null
}
```

Этот результат содержит состояние целиком, а не только изменившиеся поля.
Формат полного снимка соответствует существующей задаче `dst` и её парсеру.
В обучаемое продолжение входит JSON, а после него — EOS.

У существующего `extraction` результат шире: объект с ключами `observation`
и `state`. В `observation` находятся `reaction`, `facts`, `new_topic`, `refused`,
`user_question`, `exit`: разбор именно последнего пользовательского сообщения.
`state` содержит накопленную память.

Для предлагаемой цепочки достаточно результата `dst`. Если использовать
`extraction`, на второй шаг передаётся его `state`; передавать туда ещё и
`observation` по умолчанию не планируется.

## 6. Какие секции получает генератор ответа по состоянию?

Второй шаг имеет контракт:

```text
Инструкция поведения + S_t + H_t + U_t → R_t
```

| Секция | Что должно быть |
| --- | --- |
| Инструкция | Правила общения и требование вернуть только следующую реплику ассистента |
| Текущее состояние | Полный проверенный снимок `S_t`, предсказанный первым шагом |
| История | Та же предыдущая переписка, что использовалась при извлечении |
| Новое сообщение | То же пользовательское сообщение `U_t`, однократно |

Возможный шаблон:

```text
system: You are a friendly, curious and respectful conversational assistant.
Follow the user's lead. Do not repeat answered questions.
Respect refusals and requests to end.
Use the conversation and the current state to choose an appropriate continuation.
Return only the next assistant reply, without JSON or an action label.
Current state: {current_state_json}
{history_messages}
user: {user_message}
assistant:
```

Этот шаблон потребуется использовать и при обучении новой задачи, и при её
вызове. Одна инструкция без соответствующих обучающих примеров не заменяет
обучение модели этому контракту.

Секции `action` нет. Выбор следующего поведения и формулировка ответа обучаются
через одну текстовую цель. Модель не должна сначала выводить `ASK(activity)`
или JSON с ключом `response`.

Для сообщения `It is evening.` возможный выход:

```text
What are you doing?
```

После реплики идёт EOS. Пользователь получает только текст. Формулировка здесь
иллюстративная: это пример подходящего поведения, а не результат запуска модели.

## 7. Что сохранять и как обрабатывать следующий ход?

После успешного выполнения обоих шагов сохраняются:

| Данные | Для чего используются |
| --- | --- |
| `U_t` и фактический `R_t` | Добавляются в историю следующего хода |
| Предсказанный `S_t` | Становится предыдущим состоянием на следующем ходе |
| Номер хода и диагностические результаты | Помогают связать снимок с перепиской и исследовать ошибки; не являются репликами |

Текст JSON состояния не добавляется как обычное сообщение ассистента в историю.
Память хранится отдельно. Приложение проверяет формат, но не подменяет модельные
факты эталонными и не выбирает за модель действие.

Продолжим пример:

```text
user: It is evening.
assistant: What are you doing?
user: I would rather not say.
```

На втором ходе первый шаг получает сохранённый `S_1`, предыдущие две реплики
и последнее сообщение. Он должен учесть, что ассистент спросил о занятии,
а пользователь отказался отвечать.

Ожидаемые изменения относительно `S_1`:

| Поле | Значение в новом состоянии |
| --- | --- |
| `known.activity` | `null`: отказ не сообщает занятие |
| `statuses.activity` | `declined` |
| `asked` | `["activity"]` |
| `attempts.activity` | `1` |
| `last_action` | `ASK`: это уже произнесённый вопрос |
| `pending` | `null`: пользователь отреагировал на вопрос |

Известное время суток остаётся `evening`. Генератор ответа получает новый снимок
и должен уважать отказ; например, может спросить о настроении вместо повторного
вопроса о занятии.

Обновление этих полей в предлагаемом runtime должно происходить через
предсказание модели. Вызов `commit_action()` для исправления её памяти не входит
в этот протокол.

Если первый шаг вернул некорректный JSON или генерация не завершилась, следующий
шаг не получает выдуманное состояние. Неуспешный ход остаётся ошибкой/черновиком
и не заменяет последнюю успешно сохранённую пару состояния и переписки.

## 8. Почему нужно согласовать обучающие примеры состояния?

В текущих отдельных задачах `dst`/`extraction` исходное `state_before` уже
учитывает предыдущее действие ассистента. В предлагаемом протоколе сохранённое
`S_(t-1)` относится к моменту **до** предыдущего ответа. Это разные входы.

Для обучения новой цепочки из канонического эпизода нужно собирать пример так:

1. На первом ходе взять пустое состояние.
2. На следующем ходе взять состояние предыдущего хода после пользователя,
   но до ответа ассистента: `turns[t-1].state_before`.
3. Передать переписку до текущего сообщения, включая предыдущий ответ.
4. Добавить текущее сообщение пользователя.
5. Целью сделать `turns[t].state_before` — состояние после текущего пользователя
   и до текущего ответа.

Здесь `t` — индекс хода в `turns` канонического эпизода. Его `state_before`
означает «до ответа ассистента»; поле `state_before` экспортированного примера
`extraction` означает «до сообщения пользователя». Название совпадает,
но временная граница отличается.

В обучении предыдущие ответы и состояния берутся из обучающего эпизода. В чате
на их месте находятся собственные ответы и состояния модели. Качество нужно
проверять и в таком режиме, поскольку ошибки могут накапливаться.

## 9. Что передавать в режиме прямого ответа `history`?

Контракт одной генерации:

```text
Инструкция поведения + H_t + U_t → R_t
```

| Секция | Содержание |
| --- | --- |
| Инструкция | Правила общения из `PERSONA` |
| История | Предыдущие сообщения пользователя и ответы ассистента |
| Новое сообщение | Текущий ввод пользователя |

Секций состояния, наблюдения и действия нет ни во входе, ни в цели обучения.
Модель должна определять факты и выбирать продолжение по самой переписке.

Пример входа с текущей `PERSONA` и форматом `plain`:

```text
system: You are a friendly, curious and respectful conversational assistant. Follow the user's lead. Do not repeat answered questions. Respect refusals and requests to end.
user: It is evening.
assistant: What are you doing?
user: I would rather not say.
assistant:
```

Пример подходящего продолжения:

```text
How are you feeling?
```

В память следующего хода добавляется только пара сообщений пользователя и
ассистента. Диагностические метаданные можно хранить отдельно, но передавать
их модели не требуется.

Если ранние реплики удаляются из-за ограничения контекста, содержащиеся только
в них факты перестают быть доступны этому режиму. Отдельного снимка памяти,
который сохранил бы эти факты, здесь нет.

Обучение этого режима уже доступно:

```powershell
python trainer.py --task history --model gpt2 --epochs 2 --output runs/history
```

Команда использует канонические эпизоды из `data/`. Она создаёт отдельную модель
для задачи `history`; текущий `chat_runtime.py` пока принимает только UBAR.

## 10. Какие цели обучения и маски нужны?

| Задача | Входной контекст | `completion` |
| --- | --- | --- |
| Обновление состояния в предлагаемой цепочке | Инструкция + предыдущий снимок + переписка с текущим пользователем | Полный обновлённый JSON |
| Предлагаемая `state_response` | Инструкция + обновлённый снимок + переписка с текущим пользователем | Только ответ ассистента |
| Существующая `history` | Инструкция + переписка с текущим пользователем | Только ответ ассистента |
| Существующая `response` | Инструкция + обновлённое состояние + действие + переписка | Только ответ ассистента |

Для этих отдельных задач loss считается по токенам `completion` и нативному
EOS токенизатора. Токены входного контекста и padding имеют метку `-100`.
Контекст при этом доступен модели через attention: маска loss не скрывает его.

EOS добавляется при токенизации в [data.py](data.py). Не нужно записывать строку
`eos_token_id` или вручную добавлять ChatML-маркеры в датасет. В примерах выше
EOS не показан как видимый пользователю текст.

На обучении `state_response` сначала можно использовать эталонный текущий снимок.
При оценке всей двухшаговой цепочки он обязательно заменяется предсказанным.
Оценка только с эталонным состоянием измеряет ответ при правильной памяти и
не учитывает ошибки извлечения.

Два шага могут выполняться двумя отдельными моделями либо одной GPT-2,
совместно обученной обеим задачам с различимыми инструкциями. Совместное
обучение этой пары задач сейчас не реализовано. Два вызова одной модели всё
равно остаются двумя генерациями; состояния не становятся скрытым «thinking».

## 11. Как завершать реплику и весь разговор?

EOS означает завершение текущего результата: JSON состояния или текстовой
реплики. Он сам по себе не означает, что пользователь больше не может писать.

В текущем UBAR чат закрывается по предсказанному действию `CLOSE`. В режимах
без отдельного действия такого сигнала нет. Поэтому для них базовый вариант —
заканчивать реплику по EOS и позволять пользователю явно завершить или сбросить
сессию. Автоматическое закрытие потребует отдельно определённого сигнала.

`wants_exit` описывает намерение пользователя в состоянии, но не заменяет EOS.
Не нужно незаметно добавлять `closed` в текстовую цель `history`: это изменило
бы обещанный формат «только ответ».

## 12. Что требуется изменить для реализации и как сравнить качество?

| Область | Необходимая работа |
| --- | --- |
| Сборка входов | Добавить контракт ответа по состоянию без `action`; зафиксировать границу предыдущего состояния |
| Данные | Собирать согласованные примеры обновления состояния и ответа из тех же эпизодов |
| Обучение | Добавить новую задачу; при выборе одной модели — отдельный режим смеси задач |
| Чат | Добавить двухшаговый режим и поддержку `history`; сохранять собственные результаты модели |
| Оценка | Добавить оценку новых цепочек с собственной предысторией и, для двух шагов, предсказанными состояниями |

Текущая настройка бенчмарка `context=predicted` разрешена только для полной
цепочки DST → policy → response. Оценка `history` на эталонной переписке уже есть,
но она не заменяет будущую проверку диалогов с собственными ответами этого режима.

Для сравнения нужны одинаковые отложенные эпизоды, правила ограничения контекста
и зафиксированный бюджет обучения. Проверяем прежде всего поведение:

- повторные вопросы об уже сообщённых фактах;
- повторные запросы после отказа;
- реакцию на вопросы пользователя и просьбы завершить разговор;
- сохранение фактов и уместность продолжения темы;
- накопление ошибок при использовании собственных ответов;
- время ответа и число генерируемых токенов.

В двухшаговом режиме дополнительно измеряются корректность JSON и точность
состояния. В `history` явного состояния нет, поэтому качество памяти оценивается
по поведению, а не по несуществующему JSON-выходу. Отсутствие метки действия также
не позволяет напрямую считать точность `policy` без отдельного способа разметки
сгенерированных ответов.
